# Contributing to Platform Atlas

This doc is the source of truth for how this codebase is organized and how to
work on it without breaking its invariants.

## Quick start

```bash
npm run dev       # Vite dev server at localhost:5173
npm run typecheck # tsc --noEmit, fails fast on type errors
npm run validate  # catalog integrity: dangling refs, duplicate cells
npm run build     # typecheck + Vite build
```

No test runner yet. `typecheck` + `validate` are the current correctness gates.

### Why this shape

- **`catalog/` is a pure data module.** No React, no side effects, no DOM. It can
  be imported from anywhere without creating cycles. Adding a product is adding
  a row in `products.ts` and `categories.ts` — nothing else changes.
- **`map/` is the only place that touches the canvas.** Layout, drawing, and
  zoom bindings live together. Nothing outside `map/` knows the canvas exists.
- **One stylesheet.** The app is small enough that a single `styles.css` with
  BEM-ish class names is simpler than CSS modules or a design-token pipeline.
- **No routing library.** The view is a three-state machine (`map | roadmap |
  guide`). Adding a router would add bundle weight and indirection for three
  views.

## Code conventions

### TypeScript

- **Strict mode on.** `tsconfig.json` has `strict: true`. Do not weaken it.
- **No `any`.** Use `unknown` if the type is truly unknown, then narrow.
- **Interfaces over types for object shapes.** Use `type` only for unions,
  intersections, and mapped types.
- **Explicit return types on exported functions.** Helps the reader and catches
  drift.
- **No barrel re-export cycles.** `catalog/index.ts` re-exports from sibling
  modules, but those modules never import from `index.ts`.

### React

- **Function components only.** No classes.
- **Props as interfaces, not inline objects.** Named interfaces live near the
  component or in a `types.ts` next to it.
- **Event handlers: `onX` naming.** `onSelect`, `onClose`, `onOpenGuide`.
- **No inline object/function props.** Extract `onClick` handlers and style
  objects to named constants or component-local variables.
- **One component per file.** No co-locating multiple components in one `.tsx`
  unless they are private helpers that cannot be reused.

### File naming

- **Components:** `PascalCase.tsx`. `ProductDetail.tsx`, not `product-detail.tsx`.
- **Data modules:** `camelCase.ts` for data, `kebab-case.ts` for scripts.
- **Types shared across modules:** live in `types.ts` next to the data they
  describe, then re-exported via `index.ts`.

### CSS

- **BEM-ish class names.** `.detail`, `.detail-head`, `.detail-head h2`.
- **One class per rule, no nesting.** This project targets plain CSS; no Sass,
  no CSS modules, no Tailwind.
- **Variables in `:root`.** `--bg`, `--surface`, `--fg`, `--muted`, `--line`,
  `--accent`, plus font vars. Add new ones at the top of `styles.css`.
- **Mobile breakpoint:** `@media (max-width: 760px)`. Do not add more
  breakpoints without a design doc decision.

### Catalog data

- **`products.ts` is auto-generated.** Do not hand-edit it. Run
  `node scripts/extract-catalog.mjs` after editing the legacy source or
  `categories.ts`.
- **`categories.ts` and `edges.ts` are hand-authored.** These are the design
  decisions. Changing a category name or an edge is a design change, not a data
  tweak.
- **Guide data is optional and inline.** The `guide?: ProductGuide` property on
  `Product` is the only hand-authored per-product content beyond the initial
  `what` blurb. Guide content lives in `products.ts` for now; when it grows
  beyond a handful of products, move it to a per-product JSON or a CMS.
- **Validation runs in CI.** `npm run validate` checks for dangling references
  and duplicate cells. Do not commit catalog changes that fail validation.

## Git conventions

- **Main branch only.** No feature branches for small changes. Commit directly
  to `main`, then push.
- **Conventional commits, short body.** One-line subject, optional body that
  explains why, not what. The diff already shows what changed.
  ```
  fix: hide scrim on desktop
  
  The .scrim base rule was inside the mobile media query, so desktop
  rendered an unstyled <button>. Move it to root level.
  ```
- **No Co-Authored-By trailers.** No attribution lines in the commit message.
- **Atomic commits.** One logical change per commit. If a refactor and a bugfix
  are unrelated, separate them.
- **3–5 commits per working session.** More than that is a sign the changes
  should have been split across sessions.

## Architecture rules

These are non-negotiable. If a change breaks one of these, it needs a design
doc update first.

1. **Catalog lives in code. Study state lives in Postgres.** They have different
   lifecycles. A catalog edit is a PR; a study state edit is a user action.
   Never mix them.
2. **`catalog/` has no React imports.** It must be importable from anywhere
   without pulling in the DOM.
3. **Canvas drawing is confined to `map/render.ts`.** No component touches the
   canvas context directly.
4. **The view is a state machine.** `view: 'map' | 'roadmap' | 'guide'`. Views
   are mutually exclusive. No nested routes, no modals that pretend to be views.
5. **No runtime data fetching.** The catalog is bundled. If the catalog needs
   external data, it should be injected at build time, not fetched at runtime.
6. **No secrets in client code.** Groq API keys, if used, go through a backend
   proxy. Never call LLM APIs directly from the browser.

## Roadmap conventions

- **Roadmap lives in `src/roadmap.ts`.** Phases and milestones are typed
  `Phase[]` and rendered by `RoadmapPage.tsx`.
- **When a milestone ships, flip its `status` to `'done'`.** Do not remove it.
  The roadmap is a historical record.
- **Add new milestones as `'planned'`** with a `doc` field pointing to the
  design doc that governs them.
- **Phase 5 is Intelligence** (recommendations, guides, LLM features). New
  AI-related milestones go there unless they belong to an earlier phase's
  polish work.

## Adding a product (step by step)

1. Add the product row to `scripts/legacy-catalog.html` or directly to
   `src/catalog/products.ts` if it is a brand new product.
2. Add the category entry in `src/catalog/categories.ts` with the product id in
   its `productIds` array.
3. If the product has a layer dependency, add an edge in `src/catalog/edges.ts`.
4. Run `npm run validate`. Fix any dangling references.
5. Add a `guide` object to the product row if you have deep-dive content.
6. Run `npm run typecheck`.
7. Commit.

## What's not here yet

- **No test framework.** `vitest` is the likely choice. Priority: the
  recommendation engine, catalog validation, and scheduler math.
- **No lint/format.** `eslint` + `prettier` are standard choices. The current
  codebase is small enough that manual consistency works, but it won't scale past
  ~15k LOC without automation.
- **No CI.** GitHub Actions should run `typecheck`, `validate`, and `build` on
  every push.
- **No i18n.** All strings are inline. If localization ever happens, extract
  strings to a `messages/` module before translating.
